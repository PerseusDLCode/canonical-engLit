* TODO Build Schmidt record-extraction pass 1: identity and oRef
:PROPERTIES:
:CUSTOM_ID: phase1/schmidt-extract-identity
:ASSIGNEES: Claude Code
:DEPENDS: phase1/sense-boundary-survey

Read [[file:schmidt-record-extraction-strategy.org][schmidt-record-extraction-strategy.org]] first -- it records the
decisions this task implements and the evidence behind them. Summary of
what changed: Schmidt's Lexicon is a database, not a text; the P4
source (=Renaissance/Schmidt/copyright/schmidt.xml=) retains structure
the P5 derivative lost; we regenerate from P4 through reviewable
intermediate tables rather than continuing to mutate the P5 file.

*Repository:* this work does *not* go in =canonical-engLit=. It lives in
a new repo, =schmidt-lexicon-workshop=, which produces generated TEI
that is then delivered here. The =schmidt-tools= branch of
=corpus-tools= migrates into it. Rationale in the strategy document
§Where this lives; the short version is that a canonical repo is a
published dataset and intermediate tables under active review are not
part of that contract.

First task in the new repo is therefore to set it up: vendor the P4
source pinned by checksum (do not move or copy it into version control
as an editable file), migrate the =schmidt-tools= scripts, and
establish the =make verify= target described below before writing the
extractors.

This is the first of five extraction passes and covers the two fully
deterministic ones. Scope is deliberately narrow: it exists to prove
the pipeline shape cheaply.

*In scope:*
1. *Identity restoration.* Recover =@key= from the P4 source as
   =@xml:id=. Both files hold 20,101 =<entryFree>= elements in the
   same order, so this is a positional join. =@key= is unique across
   all 20,101 entries and already disambiguates homographs
   (=Bate1=/=Bate2=, =A1=--=A7=); 1,922 headwords have more than one
   entry. Emit =entries.tsv= (=key=, ordinal, =orth= text) and verify
   the join by comparing normalized =<orth>= strings across the two
   files, not by trusting position alone. Report every mismatch; do
   not repair silently.
2. *=<oRef>= conversion.* Convert both headword-elision conventions:
   dash-elision (=--d captives=, 19,652 tokens in 4,664 entries;
   closed suffix inventory, commonest =s= 8,113 / =ed= 3,996 / =ing=
   2,686 / =d= 2,129) and initial-letter abbreviation (=a. the fire=,
   ~70,700 tokens in 11,407 entries). Both occur inside =<emph>= spans
   as well as =<quote>= (1,316 cases) -- handle both contexts. Emit
   the observed suffix inventory as =suffixes.tsv= for review; do not
   hard-code it in the script.

*Required of both passes -- the coverage assertion.* For every entry,
the concatenation of everything extracted into fields, plus everything
explicitly classified as consumed-delimiter or declared-noise, must
reconstitute the original entry string exactly. Tokenizer discipline:
account for every character of the input. This is not optional and not
deferrable to a later pass -- it is the check whose absence let the
P4→P5 migration drop 20,101 =@key= values unnoticed. A pass that
cannot state what it discarded is not finished.

*Out of scope:* =<gramGrp>=, =<def>=, sense splitting, cross-reference
resolution, ~==~ handling, and TEI generation. Do not write a
generator yet. The intermediate tables are the deliverable.

*Provenance requirements (set up now, exercised later).* Because the
workshop is separate from the dataset, generated output must carry its
own origin or the separation reproduces the amnesia we are fixing:
- Every generated TEI file gets a =<teiHeader>/<encodingDesc>/<appInfo>=
  stamp naming the tool, its version, the workshop commit, and the
  sha256 of the P4 source it was generated from. See the strategy
  document for the exact shape.
- Generated files are marked =DO NOT EDIT=, and that mark is enforced
  by a =make verify= target that regenerates into a temp directory and
  diffs against the committed output. An advisory comment is not
  sufficient; the diff is the mechanism that stops the TEI from
  quietly reacquiring authority over the tables.

*Constraints:*
- The P4 source is read-only input. Do not modify it.
- Do not modify =schmidt.lexicon.perseus-eng1.xml=. It is being
  superseded, not repaired.
- Punctuation is syntax: parse delimiters before discarding them, and
  do not add a normalization step that strips colons, ~==~, or
  parentheses ahead of the parser.
- =<bibl @n>= in the P4 source is unreliable (confirmed: =n="shak. mv
  5.1.137"= on =Shr. Ind. 1, 137=). Display text is authoritative.
  Citation resolution is a later pass and depends on the existing
  233,265 resolutions, which must be extracted to =citations.tsv=
  rather than recomputed.

*Open schema questions are Cliff's, not Claude Code's* -- see the
strategy document §Open schema questions. Do not resolve =<oRef
@type>=, =<cit>= child order, or ODD customization by implementation
choice; flag and ask.

*Why now.* Documentation, code and data currently disagree, and the
disagreement is about to become a data loss. =alignment-oracles.org=,
=forum.org= =#citations/globe-recap= and both re-derivation agenda
entries all state that transcribed anchors carry =@source=. They do
not: =globe_lineation.py= has no such attribute and neither shipped
play file contains one. The convention that actually works today is
presence/absence of =@n= -- which holds *only because nothing yet
interpolates numbers*. =phase1/alignment-oracle-*= will interpolate.
The moment it does, =@n= means two different things and nothing
distinguishes evidence from inference. That distinction's loss in the
2025 migration is the thing this whole line of work exists to repair;
losing it again by omission would be worse than losing it by accident.

*Design.*
- A Globe milestone whose =@n= came from a transcribed P4 number
  carries =source="#globe-edition"=. One whose =@n= was derived any
  other way (interpolation, oracle fit) carries =@n= and no =@source=.
  A milestone with no =@n= carries no =@source=.
- The pointer target is a =<bibl>= in =<sourceDesc>= -- *not* a
  =<witness>=. Settled 2026-09-10: =<witness>= belongs to =<listWit>=
  and exists to be pointed at by =@wit= in a critical apparatus. Using
  it would assert that this document collates witnesses. It does not;
  it is an annotation surface for Globe act/scene/line citations.
  =<bibl>= makes the weaker, true claim.
- The =<bibl>= describes *the Globe edition* (Clark and Wright,
  Macmillan, 1864 and reprints), not a copy. The Globe's lineation is
  stable across printings -- that stability is why it became the
  citation standard -- so the edition is what is being cited. Add a
  note recording that these numbers were keyed from an unidentified
  printing c.2003 and survive in the P4 source. One entry, carrying
  both the stable claim and the honest gap.
- *Do not name a specific copy.* Cliff's own printings differ: the
  Google Books 1866 Macmillan puts Lear at p. 847 and Antony at p. 911,
  while the Internet Archive copy in use has Antony at p. 971 -- it is
  a Nelson Doubleday reprint "arranged in their chronological order",
  so pagination differs by arrangement. Digitisations are verification
  tools for the reconciliation work; they belong in the interval
  reports, not in =sourceDesc=.

*F1 milestones get no =@source=.* Reversing an earlier instruction in
this entry. =@source= earns its place on Globe milestones because it
*discriminates*: 274 carry numbers read off a page, 3,352 do not, and
once the oracle interpolates, nothing else marks the difference. F1 has
no such division -- all 3,301 are numbered, all arrived by the same
route, and nothing will ever interpolate more of them (aligning to the
Bodleian or to Folger would add a *different* reference system with its
own =@ed=, not fill gaps in this one). A constant repeated 3,301 times
per file is noise wearing the costume of data, and worse, an attribute
that looks informative on elements where it is not.

Instead, state it *once per document*, at the level of the system: a
=<bibl>= in =<sourceDesc>= or a note in =<encodingDesc>= recording that
the F1 reference system's origin is unidentified -- it matches neither
Bodleian Folio text-line numbering (drift +3 to +103 across Lear) nor
Folger FTLN (drift −6 to +342). Reference it from the F1
=citeStructure= if that makes it reachable from the declaration.

*General rule, worth stating in the ODD:* =@source= marks evidence
*within a class where some members are not evidence*. Where every
member shares a provenance, say it once at the level of the class.
