** Shakespeare source edition
:PROPERTIES:
:CUSTOM_ID: encoding/shakespeare-source-edition
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-08-11
:DISPOSITION: adopt
:END:

Which Shakespeare edition to use as the primary text in Perseus MVP,
given that: the existing Perseus Globe encoding lacks =citeStructure=
and has quality issues; the Folger/DraCor edition (CC BY-NC 3.0) has
superior engineering (FTLN + act.scene.line, TEI Simple); and the
reference works (Abbott, Schmidt, Onions, Dyce) all cite by Globe
act.scene.line.

Research summary in [[file:shakespeare-editions-comparison.org][shakespeare-editions-comparison.org]] and
[[file:citing-shakespeare.org][citing-shakespeare.org]].

Key findings:
- Greg's position (from group meeting): the canonical text for
  Shakespeare is the First Folio; Globe is a derived edition. Perseus
  should support multiple editions as it does for classical texts.
- CC BY-NC 3.0 on the Folger edition is acceptable: Perseus's focus
  is non-commercial scholarship; the F1 edition can be swapped out
  later without affecting the citation graph research.
- The DraCor ShakeDraCor repo (cloned locally) provides TEI with both
  FTLN (in =xml:id="ftln-NNNN"=) and act.scene.line (in =@n="1.1.27"=)
  on every line element — the mapping is directly extractable.
- Martin Mueller's tokenized Folger texts
  (=martinmueller39/FolgerShakespeareTokenized=) add word-level
  linguistic annotation for future NLP work.

*** Decision
[2026-08-11] DraCor/Folger as primary edition for MVP; Globe encoding
retained as a second edition. The CorpusMap (=corpus-tools=) provides
bidirectional Globe↔FTLN translation. Reference work citations
(Schmidt, Abbott, etc.) resolve through Globe act.scene.line, then
translate to FTLN for linking to the Folger text.

** =<lb>= elements and Globe line numbering
:PROPERTIES:
:CUSTOM_ID: encoding/lb-and-line-numbering
:ASSIGNEES: Cliff, Claude Chat, Claude Code
:SOURCE: chat/2026-08-12
:DISPOSITION: adopt
:END:

The existing Globe encoding had three classes of problems with line
milestones: (1) all =<lb/>= placed at end of lines rather than
beginning per TEI P5; (2) F1 TLN milestones (=<lb ed="F1" n="..."/>= )
embedded in the Globe text — a conceptual muddle; (3) Globe =<lb ed="G">= elements mostly unnumbered, with the =cRefPattern= working by
positional counting. Full analysis in [[file:globe-line-numbering-report.org][globe-line-numbering-report.org]].

Research established:
- Numbered =<lb ed="G" @n>= are primarily a *prose* device; in verse,
  =<l>= is the natural citation unit and unnumbered =<lb ed="G"/>= are
  redundant.
- Globe numbers should be transferred to =@n= on =<l>= elements,
  then interpolated between anchors per scene.
- =@part="N"= on =<l>= and =<p>= is an lxml DTD-materialization
  artifact; strip it (keep only I, M, F, Y).
- F1 =<lb>= elements removed: TLN data now comes from DraCor via
  the CorpusMap, not from milestones embedded in the Globe text.
- 7 Priority-1 anchor errors (backward-running Globe numbers within
  scenes) identified; need correction against a printed Globe edition.
  See [[file:globe-line-numbering-report.org][globe-line-numbering-report.org]] §Priority 1.
- 9 plays have no Globe number anchors at all (1h4, 1h6, 2h4, 2h6,
  3h6, ant, aww, per, tro): line numbers there are interpolated counts,
  not verified against print.

*** Decision
[2026-08-12] Strip F1 =<lb>=; strip unnumbered =<lb ed="G">= from
verse; transfer =@n= from numbered =<lb ed="G">= to enclosing =<l>=;
interpolate remaining verse line numbers per scene. Prose: retain
=<lb ed="G" @n>= in correct TEI position (beginning of line). All
implemented in =corpus-tools= and =src/mvp/= XSLTs; see =agenda.org=
for DONE items. Priority-1 errors and ungrounded plays are flagged for
manual review, not yet corrected.

** Citation encoding: =<bibl>= vs =<ref>=
:PROPERTIES:
:CUSTOM_ID: citations/bibl-encoding
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-08-14
:DISPOSITION: adopt
:END:

The reference works encode Shakespeare citations as =<bibl n="shak. lr
2.4.261">= — a structured but machine-opaque format. Question: should
the encoding be revised to use =<ref @target>= with a CTS URN?

TEI semantics distinguish =<bibl>= (bibliographic reference — a work
as source) from =<ref>= (cross-reference — a specific location in
another text). Shakespeare citations in commentary are evidence
pointers (here is an instance of this usage), which is =<ref>=
territory. The =@n= attribute was always a workaround for the absence
of machine-readable URIs.

The =@cRef= attribute requires a =<refsDecl>= in the TEI header; since
CTS URNs are proper URIs, =@target= is correct — no header declaration
needed.

Pattern for bare citation (Schmidt):
#+begin_example
<ref target="urn:cts:engLit:shakespeare.lr.globe:2.4.261">Lr. II, 4, 261</ref>
#+end_example

Pattern for quoted citation with attribution (Onions):
#+begin_example
<cit>
  <quote>his abject object,</quote>
  <bibl><ref target="urn:cts:engLit:shakespeare.h8.globe:1.1.127">H8 I. i. 127</ref></bibl>
</cit>
#+end_example

=<bibl><ref target>= preferred over =<bibl target>= for consistency
across patterns, at the cost of some terseness.

*** Decision
[2026-08-14] Replace =<bibl @n>= with =<bibl><ref @target>= (for
attributed citations) and bare =<ref @target>= (for inline citations
in running text). =@target= carries a CTS URN using the citation
family convention below. Retain =<bibl @n>= in source files until the
resolver is written and URN naming is settled (Phase 0a).

**** UPDATE <2026-08-25 Tue>
The CTS URN format has been determined; the wrapping <bibl @n>
elements may now be removed.



** CTS URNs, citation families, and the work/edition problem
:PROPERTIES:
:CUSTOM_ID: citations/cts-urns-and-citation-families
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-08-14
:DISPOSITION: adopt (pragmatic stance); open (theoretical)
:END:

The fundamental problem: CTS's work/version distinction presupposes a
stable, edition-independent textual identity to which a canonical
citation scheme can be attached. For Shakespeare this breaks down in
two ways: (1) there are two competing citation conventions (Globe
act.scene.line, Hinman/Folger TLN) neither of which is universal;
(2) for plays like Lear, Q1 and F1 are not witnesses to the same
underlying work but genuinely different texts, so there is no
work-level citation that is edition-independent.

The CTS spec requires the scholarly community to establish a single
canonical citation scheme for each work, but provides no mechanism for
cases where the community has not done so, or where the decision is
contested. The Homer Multitext handles multiple witnesses by treating
each manuscript as a version URN — but this works only when all
witnesses are variants of the same underlying text, not when (as with
Q/F Lear) the texts represent separate authorial or theatrical states.

*The concept of citation families:* what sits in the CTS version slot
should be a *citation authority* — a named scholarly convention for
how a work is divided and numbered — not an edition. Editions are
witnesses to (or implementations of) a citation authority, not the
authority itself. This distinction is not made in the current CTS spec.

Two families for Shakespeare:
- Globe (act.scene.line): `urn:cts:engLit:shakespeare.lr.globe:2.4.261`
- First Folio / TLN: `urn:cts:engLit:shakespeare.lr.f1:1664`

*File naming* (edition-level, separate from citation family):
- =shakespeare.lr.folger-eng1.xml= — DraCor/Folger, FTLN-based
- =shakespeare.lr.globe-eng1.xml= — Globe encoding, act.scene.line

The CorpusMap in =corpus-tools= functions as a provisional registry,
mapping between citation families. A formal registry (declaring
citation schemes, their authorities, and conversion tables) is what
the CTS architecture needs but does not have.

This problem deserves a paper, which Cliff will write. The paper's
argument: CTS's version slot encodes two logically distinct things —
citation convention and editorial text — which should be separated.
The "citation family" concept is what needs to sit in that slot.

*** Decision
[2026-08-14] Pragmatic stance for this project: use citation family
identifiers (=globe=, =f1=) in URN passage references; use
=folger-eng1=, =globe-eng1= as file-level edition identifiers.
Document the distinction explicitly. Treat the CorpusMap as the
provisional registry. Ratify naming with Alison Babeu and Greg Crane
before committing URNs to encoded files. Paper deferred to later.

**** Update
Alison and Greg agree with this approach. We should implement it.

** Globe↔FTLN mapping: approach and tool
:PROPERTIES:
:CUSTOM_ID: citations/globe-ftln-mapping
:ASSIGNEES: Cliff, Claude Chat, Claude Code
:SOURCE: chat/2026-08-14
:DISPOSITION: adopt
:END:

Required for resolving Globe act.scene.line citations (Schmidt, Abbott,
Onions, Dyce) to FTLN for linking to the DraCor/Folger text.

The OS Shakespeare SQL database lacks the mapping data. The right
source is the DraCor/Folger TEI XML, which encodes both systems on
every line element: =xml:id="ftln-NNNN"= for FTLN and =@n="1.1.27"=
for act.scene.line. Extraction is a five-line XPath.

Implemented in =corpus-tools= as =generate-line-map=, producing a
corpus-wide JSON file. The =CorpusMap= class provides bidirectional
in-memory lookup. Bidirectionality: Globe→FTLN for resolving reference
work citations; FTLN→Globe for displaying familiar citations in the UI.

*** Decision
[2026-08-14] Extract from DraCor XML; serialize as JSON; query via
=CorpusMap= class in =corpus-tools=. Implemented and working.
See =agenda.org= =corpus-tools/generate-line-map= (DONE).

** citeStructure for early modern plays with non-act top-level divs, and a throughline citation scheme
:PROPERTIES:
:CUSTOM_ID: encoding/citestructure-induction-and-tln
:ASSIGNEES: Cliff, Claude Code
:SOURCE: session/2026-08-19
:DISPOSITION: adopt
:END:

Converting ShakeDraCor plays (=import-shakedracor=, see =agenda.org=
=phase1/import-shakedracor=) surfaced two gaps in the existing
=drama-act-scene-line-cs= citeStructure template
(=corpus-tools/xslt/add-citeStructure.xsl=):

1. Several plays have real citable top-level divs outside the numbered
   acts -- Induction (Shrew, 2H4), Prologue (H5, Troilus and
   Cressida), Epilogue, and per-act Chorus (H5) -- that the template
   couldn't cite into at all (only =div[@type='act']= was matched at
   the outer level).
2. The =f1= (ShakeDraCor/Folger) editions carry Folger Through-Line-Numbers
   (=xml:id="ftln-NNNN"=) that deserve their own citation scheme, since
   TLN is the eventual First-Folio-grounded target (see
   =#citations/cts-urns-and-citation-families=), not just an internal
   cross-reference.

*** Decision
[2026-08-19] Extend =drama-act-scene-line-cs= with flat (div → line)
sibling branches for =induction=/=prologue=/=epilogue=/=chorus=,
alongside the existing nested act → scene → line branch. Add a second,
opt-in refsDecl (=xml:id="CTS-tln"=) citing every line by its
ftln-derived integer, emitted only when the pipeline is called with
=include-tln-refsdecl=true= (i.e. for =f1= editions specifically -- the
Globe files carry no ftln ids and don't get this refsDecl). Implemented
in =corpus-tools= (=add-citeStructure.xsl=, =pipeline.py=,
=import_shakedracor.py=); test coverage in =tests/test_pipeline.py=.

** citeStructure strategy for the four reference works
:PROPERTIES:
:CUSTOM_ID: encoding/citestructure-refworks-strategy
:ASSIGNEES: Cliff, Claude Code
:SOURCE: session/2026-08-22
:DISPOSITION: adopt
:END:

=phase1/citestructure-refworks= (agenda.org) was scoped assuming
Abbott/Schmidt/Onions/Dyce were roughly one problem with two shapes
(section-numbered vs. alphabetical headword). The =<bibl>= survey (see
=phase1/bibl-survey=, agenda.org; full data in
=doc/bibl-survey-report.org=) complicates that: the four works don't
just structure *themselves* differently, they encode their outbound
Shakespeare citations in four different grammars, only one of which
(Schmidt's =@n=) is machine-readable already. Onions is 91% free text,
Dyce and Abbott 100%, and Abbott's free text is interleaved with
citations to *other* authors (Jonson, Spenser, the Bible) with no
reliable syntactic marker separating them from Shakespeare citations.

Two coupled problems are in play: (a) citeStructure proper -- how a
reader/=ReferenceParser= cites *into* each reference work (Abbott by
§section/subsection/paragraph; Schmidt/Onions/Dyce by headword); (b)
resolving the =<bibl>= citations *out* to Shakespeare CTS URNs
(=phase3/bibl-resolver=, currently DEPENDS on this task). How tightly
to couple (a) and (b) -- and how uniformly to treat the four works --
is the open question. Four candidate strategies, not mutually
exclusive:

**** Strategy A -- bespoke, combined per-work XSLT
One XSLT per work that adds citeStructure *and* tags that work's
=<bibl>= citations as =<ref>= in the same pass.
- Pros: one round-trip through the pipeline per work; whoever's
  writing it stays in the context of that work's idiosyncrasies once,
  not twice; natural per-work commit/review unit.
- Cons: conflates two problems with different dependencies (citeStructure
  only needs the corpus-tools pipeline; bibl-tagging additionally needs
  the Abbott whitelist / =phase3/play-abbr-map=); front-loads the
  hardest problem (Abbott) before the easier three can ship; if the
  whitelist stalls, all four works stall together in MVP instead of
  Schmidt/Onions/Dyce becoming readable independently.

**** Strategy B -- two fully separate passes (citeStructure now, resolver later)
Keep Phase 1 narrowly about navigation-citeStructure only; leave all
=<bibl>= → =<ref>= tagging to a wholly separate Phase 3 pass, as
agenda.org currently implies.
- Pros: matches the existing DEPENDS graph; unblocks headword/section
  display in MVP without waiting on the resolver; each phase has one
  clear, checkable success criterion.
- Cons: two edit/review cycles over the same files; if Phase 3 later
  needs finer anchoring than Phase 1's citeStructure provides (e.g. an
  =xml:id= per =<bibl>= to target with =<ref>=), some of Phase 1's work
  may need revisiting rather than being purely additive.

**** Strategy C -- shared citeStructure for the three lexica, Abbott separate
Schmidt/Onions/Dyce share an identical =alpha → entryFree= structure
(confirmed in the source, not just assumed) -- write one parameterized
=lexicon-headword-cs= template for all three instead of three near-copies;
Abbott's section/subsection/paragraph structure gets its own template.
- Pros: DRY -- one fix in headword-citing logic fixes three works at
  once; matches the existing corpus-tools pattern of shared structural
  subclasses driving shared XSLT branches rather than per-corpus forks.
- Cons: uniformity has only been confirmed at the entry level sampled
  so far, not across the full ~280K entries combined -- multi-sense
  entries, run-on headwords, or cross-reference-only entries could force
  work-specific escape hatches anyway; doesn't reduce the independent
  ~7,000-error RNG cleanup Onions/Dyce need before either validates
  regardless of which XSLT strategy is chosen.

**** Strategy D -- normalize free-text citations to =@n= up front, before writing any resolver
Treat the free-text → =@n= conversion (Onions/Dyce/Abbott →
Schmidt's =n="shak. <abbr> <act>.<scene>.<line>"= convention) as its
own one-time editorial/data-repair pass, so Phase 3's resolver only
ever has to understand one format, not four.
- Pros: concentrates format-specific complexity into one reviewable,
  testable normalization pass per work instead of smearing
  format-detection across resolver code forever; produces cleaner
  source data with a benefit beyond this resolver; fixes the
  malformed-=@n= long tail (Schmidt's bare =shak. luc=, Onions'
  duplicate-token/leading-dot bugs) once, at the source, instead of
  special-casing it downstream indefinitely.
- Cons: rewrites primary citation *content*, not just structural
  scaffolding, at real scale (tens of thousands of free-text citations
  across three works) -- materially higher risk of silently
  misreading a citation than A/B/C, none of which touch citation text;
  can't start on Abbott until the author/play whitelist already
  exists, since you can't normalize a citation you can't first
  identify as Shakespeare's; harder to review than new XSLT (diffing a
  regenerated attribute against free text is less legible than
  reviewing template logic).

*** Decision
[2026-09-10] B + C, with D deferred. Two things already on the ground
argued for this rather than against it:

- Schmidt's citeStructure work already shipped decoupled from its
  bibl-tagging work (alpha-level =textpart= citeStructure landed
  separately from the wrapper-strip and orphan-merge passes) -- B is
  already the de facto pattern for Schmidt, not a new choice.
- Abbott's citeStructure (=§/subsection/paragraph=) is a structural
  question about Abbott's own document and does not need the
  author/play whitelist that its *bibl-tagging* work depends on
  (=phase3/play-abbr-map=, not started). Strategy A would have made
  Abbott's citeStructure wait on a whitelist it doesn't actually need.

Concretely: write one parameterized =lexicon-headword-cs= template
(alpha -> entryFree) for Schmidt/Onions/Dyce, escape-hatching for
exceptions if the full ~280K-entry sweep finds structural variation the
sampled check didn't; write Abbott's section/subsection/paragraph
citeStructure as its own template. Both proceed now, independent of
=phase3/play-abbr-map= and =phase3/bibl-resolver=.

Strategy D's free-text-normalization question is *not* decided here --
it is a Phase 3 resolver-design question, not a citeStructure question,
and committing to it now would be premature (it can't start on Abbott
before the whitelist exists regardless). Revisit when
=phase3/bibl-resolver= is actually designed.

** Merging orphaned citations into their <cit>
:PROPERTIES:
:CUSTOM_ID: citations/orphaned-cit-merge
:ASSIGNEES: Cliff, Claude Code
:SOURCE: session/2026-08-29 -- session/2026-09-01
:DISPOSITION: adopt
:END:

An automatic-tagging artifact, distinct from the doubled-=<cit>=
wrapper (=phase1= cleanup, already fixed) and the verbatim-duplicate-
citation-run bug (already fixed): =<cit>= only ever captured the
*first* citation following a =<quote>=, leaving every further citation
for that same quote as a bare =<ref>= sibling. E.g. printed "an
hundred, LLL IV, 2, 63. R2 IV, 16. H6B IV, 8, 59. ..." (10 citations)
encoded as =<cit><quote>an hundred,</quote><ref>LLL IV, 2, 63</ref></cit>=
followed by 9 orphaned bare =<ref>= elements. Corpus-wide: ~15,000
=<cit>= elements have at least one trailing orphaned =<ref>=, ~71,000
orphaned refs total (counts as of 2026-09-01, after the duplicate-run
collapse already removed ~9,700 of the original ~78,700).

Two problems surfaced while designing the fix, both resolved below.

*Schema constraint:* =perseus_lexical.rng='s =<cit>= content model
(=oneOrMore= of a closed element choice: =model.biblLike=,
=model.egLike=, =model.entryPart=, =model.global=, =model.graphicLike=,
=model.ptrLike=, =model.attributable=) is element-only -- no bare text
allowed as a direct child, and =<mentioned>= is not among the allowed
choices either (=<note>= is). A first merge attempt that simply moved
=<cit>='s closing tag out to enclose the orphaned run left the original
separator punctuation (=". "=, =", "=, etc.) and inline =<mentioned>=
apparatus text as bare content directly inside =<cit>=, which jing
correctly rejected (thousands of "text not allowed here" errors).
Cliff has hit this =<cit>= content-model rigidity before; no clean way
around it short of customizing the schema, which is out of scope here.

*Scope discovery:* restricting the orphan-absorption boundary to stop
at the next =<cit>=, the enclosing =</entryFree>=, *or* the next
=<lb/>= (senses change there -- see the =<lb/>=-as-sense-boundary
finding from the earlier citation-structure survey), the remaining
"gap" content between orphaned refs sorts into three shapes: pure
separator punctuation (a lone =.=, =;=, or =,=, ~57,700 instances,
semantically empty once the refs are proper siblings); recognizable
apparatus/cross-reference patterns (=(Qq. <mentioned>a hundred</mentioned>)=,
=cf. <ref>...</ref>=, =q. v.=); and a genuine "other" residual (~11,700
instances) that is prose introducing an entirely new sense/example via
a bare =<mentioned>= with its own trailing citation list, never marked
by =<cit>=/=<quote>= or =<lb/>= at all -- really the same unmarked-
sense-boundary problem already deferred to future =<lb/>=-based
=<sense>= reconstruction work, just surfacing here too. Forcing that
prose into a =<note>= would misrepresent a whole new example as mere
annotation.

*** Decision
[2026-09-01]
- Merge only through gaps that are pure separator punctuation (dropped
  -- see below) or a recognized apparatus/=cf.=/=q. v.= pattern
  (wrapped in =<note>=, satisfying the schema and matching the earlier
  =cf.=-wrapping decision). The moment a gap doesn't match either
  shape, stop the merge there (partial merge -- absorb what's safe,
  leave the rest still-orphaned) rather than guess; those residual
  cases are left for the future sense-structure pass.
- On dropping punctuation: Cliff raised, then answered, the concern
  directly -- once refs move to be adjacent siblings inside =<cit>=,
  an individual separator character's "this period separated ref A
  from ref B" meaning is unrecoverable regardless of where the
  character ends up (relocating all of them to just after the new
  =</cit>= only produces a meaningless cluster of identical
  characters, e.g. =</cit>. . . <cit>=). Not a faithful-print-encoding
  concern at this stage of the project regardless (per Cliff: "we're

** Globe lineation is synthetic; reference works as alignment oracles
:PROPERTIES:
:CUSTOM_ID: citations/alignment-oracles
:END:
<2026-09-03 Thu>

Working session tracing why Schmidt's citations resolve unevenly.
Written up in full as [[file:alignment-oracles.org][alignment-oracles.org]]; this entry records the
finding and the working arrangement. Draft under revision by Cliff on
branch =alignment-oracles= (off =mvp=).

*** The finding
Three nested failures, each invisible to validation:

1. The 2025 P4→P5 migration silently dropped Schmidt's complete
   =@key= identity system (20,101 unique keys, homographs already
   disambiguated). No error, unnoticed for a year.
2. Several =citeStructure= declarations address element patterns that
   later cleanup passes dismantled -- =ven.xml= matching nothing at
   all; every play file still declaring =.//lb[@ed='G']= with
   =position()= though =strip-lb= moved Globe numbers onto =<l @n>=
   (/King Lear/: 65 addressable =<lb>= against 2,550 numbered lines).
3. *The Globe line numbers themselves are synthetic.* Greg's P4 markup
   transcribed F1 through-line numbers densely (=<lb n="1442"
   ed="F1"/>=) but marked Globe line /boundaries/ without their
   /numbers/ (=<lb ed="G"/>=). Only sparse printed decade markers
   survive as numbered =<lb ed="G" n>=, and in Lear all 65 sit inside
   =<p>= -- so *verse has no anchors at all*. Every Globe line number
   in the corpus was produced by counting boundaries, unchecked.

   Verified against the printed Globe (Internet Archive, p. 860 and
   the Lear opening): I.1 runs +1 from before the verse begins and
   holds that offset for 286 lines; II.4 runs −1 and flips to +1 at a
   *duplicated* 160. 22 such collisions in 12 of Lear's 26 scenes.
   Duplicates break CTS addressing outright regardless of alignment.

Schmidt is right and we are wrong: printed Globe 161 is "She hath
abated me of half my train," exactly as he cites it. The same line is
162 in our Globe file and =n="179"= in the Folger/DraCor edition.

*** The method
Recover the lineation from evidence already held rather than by
transcribing 37 plays. A reference work citing densely into a text is a
large body of independent, falsifiable word-location assertions. For
each (work, act, scene), fit the integer offset δ maximising the
proportion of citations whose headword occurs at line /n/+δ.

Schmidt yields 96,704 act/scene/line citations across the plays; Lear
alone 5,072 across 26 scenes, median 136 per scene (min 12 -- short
scenes will not fit reliably). Abbott, Onions and Dyce cite Globe
lineation independently and serve as corroborating witnesses.

The fit reports its own confidence: a sharp peak means a constant
offset, solved; a mushy one means an internal duplicate or gap, and
/that/ is the scene whose page image needs consulting. A 37-play
transcription problem becomes a short list of flagged scenes.

*** Before building anything
Check whether the NVS globe↔TLN mapping tool already carries a verified
Globe lineation for /King Lear/. If it does, this is a join, not a
project. (Required by the NVS collaboration protocol.)

*** Open threads
1. Globe retention still undecided, now on better evidence: repair the
   Globe editions as the citation-bearing texts if offsets recover
   cleanly; retire them explicitly if they do not, with reasoning
   recorded in the work-level =__cts__.xml= and here.
2. Corpus-wide Schematron assertion: every declared =citeStructure=
   must match at least one node.
3. The Furness cascade (NVS) and this offset fit are the same
   procedure at different scales -- worth writing up as a method
   rather than twice as an implementation detail.
4. Feeds the CTS-URN paper: =Lr.= II, 4, 161 is not a coordinate in
   /King Lear/ but in one printing of one edition. Globe I.1.150 reads
   "Of /her/ confine"; Folger reads "Of /his/ confine". A URN scheme
   modelling the work as a single citable object has nowhere to put
   that.
5. *Bookmarked, not yet discussed:* the Alignment Oracle is a
   conspicuously Derridean figure -- an oracle that predicts what
   should already have been there; recovery of an origin that turns
   out never to have been transcribed; textual instability as the
   normal condition rather than the defect. Cliff flagged this
   <2026-09-03 Thu> as a conversation to have properly.

Found while spot-checking the re-derived =shakespeare.lr.globe.xml=
(=phase1/rederive-lear-p5=) against the actual =perseus_cts= resolver
rather than trusting the placement design by inspection alone.
=check_corpus.py='s =citation_records()= walk is unaffected (=ok=,
=d2=3626=) -- these are gaps in the two APIs a consumer would actually
use to fetch a single passage's *text*, =resolve()= and =chunks()=,
both in =perseus-cts/src/perseus_cts/cts_resolver.py=. Neither is a
defect in the Lear data or in this task's milestone placement; both
are structural gaps in the resolver when a leaf =citeStructure=
addresses =<milestone>= elements nested several levels under =<div>=,
rather than the flat =<div><p>...</p></div>= shape its own test
fixture uses.

*** Finding 1: =elements_between()= only collects elements, never tail text
=cts_resolver.py='s =elements_between()= (used by =_milestone_chunks()=,
the span-builder behind =chunks()=) walks =root.iter()=, collects every
*element* whose document-order position falls between two milestones,
and keeps only the topmost ones. A line whose actual text is the
milestone's own =.tail= -- exactly the shape this task's placement fix
produces, e.g. =<l><milestone ed="Globe" n="160"/>Return you to my
sister. <milestone ed="F1" n="1440"/></l>= -- contributes *no* elements
to that span, so =elements_between()= returns =[]= and the chunk's
text comes back empty. Verified directly against the real file: calling
=resolver._milestone_chunks()= on Lear's line-level =citeStructure=
yields 274 numbered chunks (matching the 274 transcribed anchors,
confirming the anchor count itself is fine), of which the large
majority have empty text; =urn:...:shakespeare.lr.globe.160= returns
=''=, not "Return you to my sister." A chunk only gets real text when
the span happens to contain a sub-element (a =<speaker>=, a =<stage>=)
regardless of the actual verse/prose text alongside it -- coincidence,
not correctness. This isn't specific to Globe's sparse numbering; it
would affect any milestone-delimited span whose content is plain text.

*** Finding 2: =_milestone_chunks()= doesn't compose ancestor URN components
=_milestone_chunks()= builds each chunk's URN as
=self._base_urn + delim + val= -- =val= from the matched milestone's
own =@n= only. It has no path back through the =citeStructure= tree to
the act/scene tokens the milestone sits under. Invoked directly on
Lear's line-level =citeStructure= (three levels deep: act -> scene ->
line), this produces =urn:...:shakespeare.lr.globe.160= for *every*
scene that happens to have a transcribed anchor at Globe 160 -- five
of them, since Globe numbering restarts each scene by design. The
composed, correct form (=...:2.4.160=) is never produced by this path.
=chunks()= itself doesn't hit this today only because it auto-selects
its target level as either an explicit =n="chunk"= citeStructure or,
failing that, the *penultimate* level (=_find_chunk_cs()= /
=_penultimate_cs()=) -- for Lear's three-level hierarchy that's
"scene", not "line", so =chunks()= currently yields 26 correct
scene-level =CitationChunk=s via the unrelated =_div_chunks()= path and
never reaches =_milestone_chunks()= at all. The gap only surfaces when
something calls =_milestone_chunks()= directly at a non-chunk-level, or
if a future citeStructure ever marks the line level itself as the
chunk level.

*** What does work
- =resolve()= (single-URN) correctly locates the matched node through
  the full act -> scene -> line hierarchy -- =2.4.160= resolves to the
  right =<milestone>= -- but then returns that bare node as-is with no
  span-building at all (see =_resolve_with_cs=, =return matched=). For
  a milestone leaf that node is definitionally empty, so =resolve()=
  can locate the right point but never returns text.
- The START-FORWARD span-building /algorithm/ itself (walk from a
  matched milestone to the next) is the right shape for how this
  task's milestones are now placed, and is exercised and passing in
  =perseus-cts='s own test suite (=tests/test_cts_resolver.py=,
  =MILESTONE_XML= fixture, =test_each_chunk_contains_correct_content=)
  -- on that fixture, content sits in wrapping elements
  (=<div><p>card 1 content</p></div>=), which is why the tail-text gap
  above doesn't show up there.
- The anchor data itself is sound: 274 numbered chunks from 274
  transcribed anchors, no more, no less; =citation_records()=/leaf
  depth is unaffected.

No fix attempted -- this is =perseus-cts=, a sibling repo, and outside

** Commit discipline across multiple agents and repositories
:PROPERTIES:
:CUSTOM_ID: protocol/commit-discipline
:END:
<2026-09-09 Wed>

Recurring problem, worsening as more agents (human and AI) work the
project: changes accumulate uncommitted across several repositories at
once. On 2026-09-09 there were uncommitted changes in
=canonical-engLit=, =corpus-tools= and =perseus-schemas=
simultaneously, and =citations.tsv= in the workshop had already been
generated from a dirty tree -- its provenance header reads
=commit=74e5ee7-DIRTY=, so the table cannot be reproduced from its own
record. That is the exact failure the stamping discipline was designed
to prevent.

*** Why it happens, and why "commit more often" won't fix it
The review loop has no natural commit point. A single day's Lear work
ran: Claude Code delivers the re-derivation → Cliff catches the
milestone placement → Claude Code fixes it → Claude Code finds a bug in
its own fix → Claude (chat) flags the anchor displacement from outside
→ a schema change is reverted across two repos. At no point in that
sequence is the tree in a state that reads as "done": every moment is
either *just delivered, not yet reviewed* or *under correction*. The
stopping point keeps receding while the diff grows.

Exhorting ourselves to commit more often competes directly with review,
and review wins. The fix has to attach the commit to a boundary that
already exists.

*** Two couplings that already have boundaries
1. *Stamped artifacts require a clean tree.* Anything carrying a
   provenance header -- =citations.tsv=, =lear-globe-anchor-intervals.csv=,
   a re-derived play -- cannot honestly be produced from a dirty tree,
   because the stamp would be false. Make =make regenerate= *refuse* on
   a dirty tree rather than emit =-DIRTY=. Self-enforcing, needs no
   memory, and fires exactly when the record matters most.
2. *An agenda activity note is a commit message.* Claude Code already
   writes a substantial note when a task reaches a reportable state;
   writing it *is* the moment of "this piece is done." Couple them: the
   note and the commit land together. Costs nothing, and puts the commit
   at a boundary that exists anyway.

*** The structural gap: no single working tree
This project has no one repository. A day's work routinely touches
=canonical-engLit=, =corpus-tools=, =perseus-schemas= and
=schmidt-lexicon-workshop=. Some changes are *one logical change split
across repos* -- e.g. the =orig=/=reg= revert, which is
=perseus-schemas= =e6fd910= plus the =corpus-tools= Schematron
=legacy-reg= revert. Git cannot express that relation and neither can
=agenda.org=; nothing in either record says those two commits belong
together.

Proposed convention: when a change spans repositories, put a shared
token in every commit message involved (e.g. =[xrepo: reg-orig-revert]=)
and name the same token in the agenda note. Crude, but it makes the
relation greppable from either side, which is more than we have now.

*** Related
- Branch drift is a symptom of the same thing: the Globe re-derivation
  modules (=globe_lineation.py=, =globe_anchor_intervals.py=,
  =rederive_globe_lineation.py=) were written on =corpus-tools='s
  =schmidt-tools= branch because that is where the session happened to
  be, and =xslt/schmidt-edit.xsl= is Schmidt work that now belongs in
  the workshop repo.
- Some of the 2026-09-09 disorder originated in chat-side advice: the
  workshop split was proposed without accounting for cross-repo
  commits, and Cliff was asked to hold off committing pending a chat
  edit to =alignment-oracles.org=. Coordination load added from outside
  the working tree is still coordination load.
