#+TITLE: Schmidt Lexicon Citations vs. the Globe<->TLN Map: Resolution Analysis
#+DATE: 2026-08-18
#+AUTHOR: Clifford Wulfman
#+OPTIONS: toc:t num:nil

* Overview

=corpus-tools= recently gained =tln_globe_map.py=, which builds a
corpus-wide Globe act.scene.line <-> Folger Through-Line-Number (TLN)
map from ShakeDraCor's 37 Folger-derived Shakespeare TEI files (commit
=4467d7c=). Before relying on it, we exercised it against a large,
independent real-world citation set: Alexander Schmidt's *Shakespeare
Lexicon and Quotation Dictionary* (1902), digitized at
=canonical-engLit/data/schmidt/lexicon/lexicon.xml=. Schmidt cites every
headword occurrence as =<bibl n="shak. {siglum}
{act}.{scene}.{line}">{display text}</bibl>=, using the same lowercase
play sigla and dotted act.scene.line format the map already keys on —
good alignment by construction, and a much larger, messier test than
the hand-built fixtures in =test_tln_globe_map.py=.

The map held up well: *94.42% of clean act.scene.line citations
resolved to a TLN* before any repair. One of the causes behind the
remaining shortfall turned out to be a fully-diagnosed, mechanical bug
in Schmidt's own =@n= markup, and has since been *fixed* — see "Cause
1" below and =corpus-tools='s =repair-schmidt-citations= command. After
that fix, *95.72% resolve*. None of the remaining causes are defects in
=tln_globe_map.py= itself; they trace to how Schmidt's =@n= attribute
was generated, or to gaps/typos in ShakeDraCor's own source.

*Revision note (2026-08-18, later the same day):* this report originally
claimed a second fully-verified cause — a "King Lear continuous
through-scene citation convention" — and reported citation counts about
13% lower than the true figures. Both are corrected below; see "Cause 2"
for what went wrong and why, and the note at the end of the Summary
table for the counting bug. The retraction happened *before* any fix
was built from the Lear claim, so nothing was shipped on the strength of
it.

A regression test (=corpus-tools/tests/test_schmidt_lexicon_map.py=)
guards the resolution rate and documents one concrete instance of the
baseline residual gap.

Note: the citation count above (204,766) supersedes this report's
original figure (178,215, "94.37%" resolved). The first pass extracted
citations with a regex requiring =<bibl n="= to be textually adjacent in
the raw XML; the lexicon's own formatting wraps long attribute lists
onto a new line in many places (=<bibl\n  n="shak. ...">=), and every
one of those was silently skipped. =repair-schmidt-citations= and the
updated =test_schmidt_lexicon_map.py= both parse citations properly (by
iterating =<bibl>= elements, not scanning raw text), which is how the
missing ~26,500 citations turned up. The qualitative findings below are
unaffected — the true resolution rate (94.42%) is close to the
originally-reported one (94.37%) — but every specific count in this
report has been recomputed against the corrected extraction.

* Cause 1: single-scene-Act citation collapse — FIXED (2,667 citations)

When an Act has only one scene — Tempest Act 5, Merchant of Venice Act
5, Measure for Measure Act 5, and others — Schmidt's own printed
citation naturally collapses to just "Act, Line" (there's no scene to
disambiguate). His display text confirms this directly:

#+begin_example
<bibl n="shak. tmp 5.169.458">V, 169</bibl>
<bibl n="shak. mm 5.252.26">V, 252</bibl>
<bibl n="shak. mv 5.147.88">V, 147</bibl>
#+end_example

But whatever tool generated the machine-readable =@n= attribute on
these =<bibl>= elements still forced a three-slot act.scene.line
template onto a two-component "Act, Line" citation. It dropped the real
line number into the *scene* slot and fabricated a third number from
nowhere (=458=, =19=, =1=... no discernible relationship to the real
line). The result: a well-formed-looking three-part reference
(=5.169.458=) that can never resolve, because Tempest's Act 5 has
exactly one scene and no line 169 in it.

*Detection rule:* the citation's Act, per ShakeDraCor's own =<div
type="scene">= structure for that play, has exactly one scene, and
Schmidt's display text is a bare "Roman numeral, number" pair. The fix
reconstructs =act.1.line= from the display text's own line number and
only rewrites the citation if that reconstruction actually resolves to
a TLN — never an unverified guess.

*Fixed*: =corpus-tools='s =repair-schmidt-citations= command
(=src/schmidt_citations.py= + =src/commands/repair_schmidt_citations.py=)
applies this rule mechanically. Run against the real lexicon, it found
2,667 fixable citations (2,130 distinct old->new mappings; some
citations repeat verbatim across multiple headword entries) across 11
plays:

| Play | Fixes | | Play | Fixes |
|------+-------+-+------+-------|
| tmp  |   787 | | shr  |    94 |
| mm   |   456 | | jn   |    77 |
| err  |   297 | | tit  |     1 |
| mnd  |   288 | |      |       |
| mv   |   210 | |      |       |
| tn   |   167 | |      |       |
| r2   |   167 | |      |       |
| lll  |   123 | |      |       |

Fixes are applied as surgical string substitutions on the lexicon's raw
XML text (matching each citation's exact old =n="..."= value), not by
mutating and re-serializing the parsed tree — lxml's serializer doesn't
preserve the file's hand-wrapped attribute formatting on a round trip,
which would have rewritten the whole file's whitespace for a
~2,600-attribute change. The committed diff
(canonical-engLit commit =ee629df=) touches only the changed =n=
attribute values.

This bug was the leading cause of Tempest's below-average resolution
rate (86.20% -> 97.40% after the fix) and several other plays whose
final act is a single long scene (Measure for Measure 89.74% -> 96.88%,
Comedy of Errors 86.80% -> 93.73%, Midsummer Night's Dream 90.75% ->
96.66%).

* Cause 2 — RETRACTED: there is no verified "King Lear continuous-scene" pattern

This report originally claimed a second fully-diagnosed cause: that
Schmidt's Globe source cited Lear by a continuous scene number running
straight through all five acts (1-25) rather than by act.scene, based on
reinterpreting bare "N, line" display citations (e.g. =22, 12=) as
(continuous-scene, line) and finding 15/15 sampled cases resolved
correctly. That verification was flawed and the finding does not hold.

*What went wrong:* the 15-sample check tested only the *first* 15 of
Lear's 87 bare-numeric citations, in document order. That sample
happened, by chance, to consist entirely of low numbers (1-25) that fit
Lear's real scene count. Testing the full population of 87 tells a
different story: only 2 have a number in Lear's valid continuous-scene
range at all. The other 85 have numbers like 55, 85, 124, 136 that
cannot be scene references for a 25-scene play under any interpretation.

Worse, the 2 "in-range" cases are not Lear citations. Checking their
surrounding context in the lexicon:

#+begin_example
<bibl n="shak. son 35.4">Sonn. 35, 4</bibl></cit></cit>.
<bibl n="shak. lr 1.22.12">22, 12</bibl>.
#+end_example

=Sonn. 35, 4= is a Sonnets citation with no quote of its own; =22, 12=
immediately follows it with no play abbreviation printed at all — a
Schmidt typographic convention of dropping the repeated work
abbreviation across a run of citations to the *same* work. This citation
is almost certainly =Sonnet 22, line 12=, continuing the *Sonnets*
citation, not Lear at all. Whatever tool built the machine-readable =n=
attribute apparently defaulted the run-continuation citation to the
*current play's* siglon (=lr=, Lear, presumably from the entry's
dominant context) rather than tracking which work the citation run was
actually continuing. Both of the "verified" Lear matches were
coincidences of this misattribution landing on a valid-looking TLN by
chance.

*Confirming this is a coincidence, not a real pattern:* reinterpreting
the same "bare N, N -> continuous scene" logic against Cymbeline — a
play with no Quarto/act-division history and no scholarly reason to use
continuous scene numbering — also "resolves" 8 citations to real TLNs.
=cym 5.19.7= ("19, 7") reinterpreted as continuous scene 19 resolves to
Act 4 Scene 1, line 7, TLN 2212 — a perfectly plausible-looking but
almost certainly meaningless result. With Cymbeline's TLN space holding
thousands of lines across 27 possible continuous-scene values, some
fraction of random (scene, line) reinterpretations will land on a real
TLN purely by chance. *"Resolves to some TLN" is not sufficient evidence
of correctness* — this report's original methodology treated it as such,
which is how the Lear claim survived an initial check.

*What the bare "N, N" pattern actually is:* most likely, at least in
part, exactly what the Lear example above shows — implicit continuation
of a citation run to a *different* work (often the Sonnets or another
play), where Schmidt's print drops the repeated abbreviation and the
=@n=-generation tool guessed wrong about which work continues. This
would need a *stateful* parser that tracks "current work" across a
citation run to resolve correctly — structurally the same class of
problem already known and deferred for the NVS/Furness annotations
(=nvs-annotations/shake.var.*.annot.xml=, which similarly omits
=@act=/=@scene= and inherits from a preceding annotation). It has not
been verified end-to-end and is *not* part of the current repair pass.
Pericles was also checked (it shares Lear's Quarto/act-division
history) using the same full-population methodology: only 3 of 104
bare-numeric citations resolve under continuous-scene reinterpretation,
and the rest have out-of-range numbers up to 151 against Pericles' 22
real scenes — the same negative result as Lear.

* Cause 3: 2 Henry IV's prose relineation drift (partially diagnosed)

2 Henry IV has the worst resolution rate in the corpus, 82.40% (1,064
unresolved out of 6,045 clean citations) — untouched by the Cause 1
repair, since 2H4 has no single-scene Acts. It also has the highest
prose fraction of any play in the corpus — 51.8% of ShakeDraCor's
through-lines are =<lb>= prose milestones rather than =<l>= verse
lines, against a corpus median well under half that.

Prose line breaks are a typesetting artifact of a given edition's page
— where the line wraps depends on page width, font, and the
compositor's choices — not fixed by the poet the way verse lineation
is. Two different editions of the same prose passage will not, in
general, produce the same line count, and small per-line differences
compound across a long prose scene.

This was confirmed concretely for Act 1 Scene 2 (entirely prose —
Falstaff and his page, then Falstaff's soliloquy on his gout):
ShakeDraCor's own scene ends at =1.2.256=, but Schmidt cites lines in
that scene as high as =1.2.278= — Globe's relineation runs the scene
about 22 lines "longer" than Folger's.

*This mechanism is not fully proven at the scale needed to explain
2H4's whole shortfall.* Classifying each unresolved citation as either
"beyond the end of ShakeDraCor's scene" (clear relineation overflow) or
"in range but still missing" (an isolated gap within the scene) gives:

| Type                                    | 2H4 count | % of 2H4 unresolved |
|-------------------------------------------+-----------+-----------------------|
| Overflow past ShakeDraCor's scene end      |       217 |                 20.4% |
| In-range gap                                |       847 |                 79.6% |

Only the 217 overflow cases are directly and unambiguously explained by
the relineation-drift mechanism as demonstrated above. The remaining
847 in-range gaps are consistent with the same underlying cause
(relineation drift doesn't only produce a longer tail — it can also
produce collisions *within* a scene if the two editions' line breaks
diverge and then partially re-converge), but that has not been verified
line-by-line the way the single-scene-Act mechanism was. Given how
Cause 2's superficially-plausible "resolves to a TLN" check turned out
to be worthless as evidence, no attempt was made to auto-fix this
pattern. Prose relineation remains the leading hypothesis for 2H4, not a
closed case.

* Baseline residual: isolated TLN gaps in ShakeDraCor's own source (all plays, ~1-4%)

Independent of Schmidt entirely, every play in the ShakeDraCor corpus
has a small number of Through-Line-Numbers that simply don't exist
anywhere in that play's TEI file — not missing an =@n= attribute, the
=xml:id= itself is absent. Example: Merry Wives of Windsor jumps
directly from

#+begin_example
<l xml:id="ftln-2307" n="4.4.8">Than thee with wantonness. ...</l>
<l xml:id="ftln-2309" n="4.4.10">In him that was of late an heretic, </l>
#+end_example

=ftln-2308= (which would be =n="4.4.9"=) never appears anywhere in the
file. Schmidt happens to cite =shak. wiv 4.4.9=, which can never
resolve until ShakeDraCor's source is corrected upstream. This pattern
recurs across the whole corpus at roughly 0.3%-4.4% of each play's
lines (lowest in Merry Wives itself and Henry VI Part 1; highest in
Comedy of Errors, Lear, and Macbeth), and reads as genuine editorial
practice — a Through-Line-Number slot reserved but not printed in this
edition — rather than a ShakeDraCor extraction bug. This is unaffected
by the citation-counting correction above (it was always derived
directly from ShakeDraCor's own source, not from lexicon.xml), and is
the baseline every play sits on top of, on top of which Causes 1-3 add
their own, larger effects for specific plays.

=corpus-tools/tests/test_schmidt_lexicon_map.py::test_wiv_4_4_9_is_a_known_source_gap=
documents this exact case as a regression fixture, so it doesn't get
mistaken for a map bug in a future session.

* Aside: a ShakeDraCor data bug in Othello, unrelated to Schmidt

While tracing TLN allocation gaps corpus-wide, two corrupted
=xml:id=\/=n= pairs turned up in ShakeDraCor's own
=tei/othello.xml=, sitting among an otherwise clean, sequential
run of ids in the 3600s:

#+begin_example
<l xml:id="ftln-23830" n="4.1.3"  part="F">What, </l>
<l xml:id="ftln-24080" n="4.1.29" part="F">What </l>
#+end_example

=23830= and =24080= are almost certainly typos for =2383= and =2408=
(an extra trailing zero) — Othello's ids otherwise top out around
3681. Because these ids are numerically distinct from every other TLN
in the file, =build_corpus_map= didn't raise its duplicate-key check
and the bug passed silently. It doesn't affect Globe-ref lookups (the
=n= values =4.1.3=/=4.1.29= are fine) and it isn't something Schmidt
cites into, so it's noted here rather than fixed — it would need to be
corrected upstream in ShakeDraCor's source, or worked around locally if
we ever depend on Othello's TLN values specifically.
